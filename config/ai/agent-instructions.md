# Commit messages

- コミットメッセージはできるだけ詳しく書く。
- コードから読み取れる変更内容の羅列より、コードから読み取れない背景を優先して記載する。
- なぜこの変更が必要になったのかを書く。
- プルリクエストを作成するに至った理由を書く。
- 関連する Issue、PR、バグ報告、設計上の制約があれば含める。
- コミットメッセージは最終的な変更とその背景に絞り、試行錯誤の経緯や採用しなかった機能・案は原則として書かない。
- ただし、読み手が自然に疑問に思う代替案を採用しなかった理由や、将来の判断に必要な制約がある場合は、その理由を簡潔に書く。
- 1行目は要約にする。本文には背景、理由、注意点を書く。

# プルリクエスト本文

- CI で確認できる検証内容や結果は、PR 本文に記載しない。
  テストや lint の成否、ツールのバージョン、検査ファイル数、
  examples 数、実行時間、出力ログなども同様。
- 検証について記載するのは、手動での動作確認や、
  CI でカバーできない確認事項、レビューの判断に必要な制約などに限る。
- 記載すべき検証情報がなければ、検証セクション自体を設けない。
- ただし、変更の背景や不具合の説明に必要な情報、
  ユーザーから明示的に求められた情報は記載してよい。

# コード・テスト・コメントの役割

- コードで実現方法（How）、テストで期待する振る舞い（What）、コミットメッセージで変更の背景や理由（Why）を表現する。
- コードコメントは、自然に思いつく実装や単純化をあえて採用しない理由（Why not）など、コードから読み取れない制約や注意点に絞る。
- コードを読めば自明な処理の説明や、コミットメッセージで分かれば十分な変更背景は、コードコメントに重複して書かない。
- コメントを追加する前に、命名や構造の改善で意図を表現できないか検討する。書くべき補足がなければコメントを追加しない。
- 将来の変更で制約を誤って破らないために、その場で必要な Why not は、コミットメッセージにも記載があっても簡潔にコメントとして残す。
- コメントは現在のコードに必要な情報に絞り、変更履歴や作業報告の代わりにしない。
